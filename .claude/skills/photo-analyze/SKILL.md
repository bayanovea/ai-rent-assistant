# Анализ фотографий листингов

Текстовый проход (`/analyze`) уже прочитал описания. Этот проход смотрит
на картинки и проверяет, что за словами стоит: «fully furnished» пишут
все, фото показывает, что это значит. Главный продукт прохода — не новые
факты, а **расхождения с текстом**.

Ты здесь оркестратор: картинки в твой контекст не попадают. Их читают
сабагенты — по одному на объявление. Ты собираешь их JSON и применяешь.

Вердикт, `score` и `status` не твоё и не сабагентов дело — их считает
`rules.py` из полей.

Проход запускается **по явной просьбе пользователя**, после того как он сам
просмотрел таблицу и отклонил лишнее. Сам его не предлагай и не запускай
следом за текстовым анализом: смысл в том, чтобы платить токенами только за
то, что человек уже оставил. Отклонённое руками в очередь не попадает —
вердикт из `decisions.json` перебивает `rules.py` в обе стороны.

## 1. Проверить очередь

```sh
fb-rent ai-status
```

Смотри блок «Фото»:

- `Pending: 0` — смотреть нечего, скажи об этом и остановись (разве что
  просят пересмотреть конкретные id — тогда `fb-rent photo-batch --ids <ID>`);
- `No photos: N` — у этих листингов на диске нет картинок. Скажи
  пользователю:

  > N листингов без фото. Запусти `fb-rent photos-fetch`, потом
  > вернёмся к фото-анализу.

  Это не повод останавливаться, если `Pending` при этом больше нуля:
  прогоняй тех, у кого фото есть, а про остальных скажи в отчёте.

Причины в `Pending` читаются так: `new` — прохода ещё не было, `changed` —
фотографии на диске сменились, `schema` — появилось новое фотополе.

## 2. Собрать batch

```sh
fb-rent photo-batch --limit 25
```

Команда печатает путь вида `.../ai/photo-batch-YYYYMMDD-HHMMSS.json`.
Флаги — зеркало `ai-batch`: `--all`, `--ids <ID>` (повторяемый, достаёт
объявление мимо очереди), `--out`.

Прочитай batch **без `items[].photos`** — тебе нужны `fields` (реестр
фотоколонок с `prompt` для каждой) и `requirements_md`. Пути к картинкам
уйдут сабагентам, открывать их самому незачем.

Отклонённые текстовым проходом в batch не попадают вовсе — на них токены
не тратятся.

## 3. Веер сабагентов — по одному на объявление

На каждый `item` из batch — свой сабагент. Независимые запускай **одним
сообщением**, чтобы шли параллельно (до ~12 за раз):

```
Agent(subagent_type: "general-purpose", model: "sonnet", prompt: <инструкция ниже>)
```

В промпт каждому положи:

- пути ко всем файлам из `item.photos` (это вся галерея объявления,
  сколько бы кадров в ней ни было) и требование
  открыть каждый через `Read`, пронумеровав в том же порядке: фото 1 —
  первый путь;
- `fields` из batch целиком — ключи, типы, `values`, `prompt`;
- `item.current_fields` — что по этим же полям сказал текст. Это не
  подсказка, а то, что надо проверить: расхождение здесь ценнее
  совпадения;
- `item.fb_id`, `item.photos_hash`, `item.listing_title`;
- требование вернуть **только JSON**, без пояснений вокруг.

Дисциплина для сабагента — та же, что в текстовом проходе, перенеси её в
промпт дословно:

- **Ничего не выдумывай.** Не видно на фото — `unclear` (для enum) или
  пропуск ключа (для text). Правдоподобная догадка хуже честного
  `unclear`. «Наверное, за дверью кухня» — это `unclear`.
- **Каждое непустое значение — с `ev`** в формате `"фото N: что видно"`
  («фото 3: плита на две конфорки, вытяжка, столешница»). `ev` — то, чем
  ты обосновываешь значение, а не пересказ картинки целиком.
- **Текст не отменяет фото и наоборот.** Если текст обещал `furnished:
  full`, а на фото пустые комнаты — ставь `none`/`partial` со ссылкой на
  кадр. Если фото не показывает того, о чём писал текст (парковку не
  сняли), это `unclear`, а не `no`: несъёмка — не отсутствие.
- `conf`: `high` — видно прямо в кадре; `med` — следует из ракурса или
  соседнего кадра; `low` — шаткий вывод (тогда честнее `unclear`).
- Формат значения: `{"v": <значение>, "conf": "high|med|low", "ev": "фото N: ..."}`.
- `verdict`, `score`, `status` сабагент **не заполняет** — их считает
  `rules.py`. Максимум — `comment` на 1–2 предложения про то, что видно
  на фото и чего не видно.

Отдельно про `photo_quality` — сигнал, которого нет в тексте:

- `render` — 3D-визуализация вместо съёмки (идеальный свет, безлюдный
  интерьер, «пластиковые» текстуры, повторяющаяся мебель);
- `floorplan` — только планировки, интерьера нет;
- `other_unit` — снят явно другой юнит: другая планировка, другой этаж,
  другой вид из окна между кадрами;
- `real` — реальные снимки этого объекта;
- `unclear` — не разобрать.

При `photo_quality: render` **остальные фотополя заполнять нельзя**:
рендер показывает замысел застройщика, а не квартиру. Верни только
`photo_quality` и `comment`.

Каждый сабагент возвращает один объект:

```json
{ "fb_id": "...", "photos_hash": "<из batch, дословно>",
  "comment": "Реальные снимки, мебель есть везде кроме второй спальни.",
  "fields": { "furnished": {"v": "partial", "conf": "high",
                            "ev": "фото 4: во второй спальне пустой пол, только кондиционер"},
              "photo_quality": {"v": "real", "conf": "high",
                                "ev": "фото 1: живой кадр, видны вещи хозяев"} } }
```

## 4. Собрать результат

Сложи объекты сабагентов в файл рядом с batch:
`<AI_DIR>/photo-result-<тот же ts>.json`.

```json
{ "schema_version": <тот же, что в batch>,
  "model": "claude-sonnet-5 (claude-code subagents)",
  "results": [ <объекты из шага 3> ],
  "proposed_new_fields": [] }
```

`photos_hash` копируй из batch дословно: по нему код понимает, не сменились
ли картинки между сборкой и приёмом. Не совпал — запись **пропускается**,
и это правильно: анализ описывает уже не те фотографии.

`verdict` здесь не нужен — он остаётся за текстовым проходом. Ключ,
которого нет в реестре, обрушит **весь файл** — новые сигналы идут в
`proposed_new_fields`.

## 5. Применить

```sh
fb-rent photo-apply <путь к photo-result-*.json>
```

При сомнениях сначала `--dry-run`. Команда печатает:

- сколько анализов применено;
- **расхождения** `fb_id.key: старое -> новое` — это главный результат
  прохода;
- новые автореджекты с причинами (фото может уронить объявление, если
  показало студию там, где текст обещал дом);
- пропущенные (несовпавший `photos_hash` — им нужен новый `photo-batch`);
- предложенные поля.

Фотополя пишутся поверх текстовых слиянием, после чего пересчитываются
`decide` и `score`.

## 6. Новые поля

Если сабагенты предложили что-то в `proposed_new_fields` (полезный сигнал,
видный **в ≥2 объявлениях**) — спроси пользователя через
`AskUserQuestion`, нужна ли колонка и надо ли пересматривать старые фото.
Затем:

```sh
fb-rent ai-field add --key balcony_view --label "Вид с балкона" \
  --type enum --values sea,city,yard,none,unclear --group amenity \
  --source photo --prompt "Что видно с балкона на фото" [--backfill]
```

`--source photo` — поле заполняет только фото-проход, `--source both` —
оба. `--backfill` двигает `photo_analysis_version` и возвращает все
листинги в очередь фото с причиной `schema`; тогда **вернись к шагу 2**.
Без `--backfill` идём дальше, старым листингам достанется штриховка
`c-stale`.

## 7. Экспорт и отчёт

```sh
fb-rent export
```

Отчитайся коротко:

- сколько объявлений посмотрели, сколько осталось в очереди;
- **список расхождений** — где фото поспорило с текстом, по каждому одна
  строка: что обещал текст, что видно на фото;
- `photo_quality: render` / `floorplan` / `other_unit` — по этим
  объявлениям фотографий фактически нет, о них стоит спросить агента;
- новые автореджекты с причинами;
- листинги без фото на диске — им нужен `fb-rent photos-fetch` (а если он
  скажет, что ссылок нет или они протухли — `fb-rent scrape --ids <fb_id>`).

Решение по конкретному объекту принимает пользователь через
`fb-rent reject / unreject / shortlist`. Сам эти команды не вызывай, если
не просили.
